## 確認できた原因と未確定事項

- `PdfInk` は連続同一座標をすでに省くが、近接する異なる座標は保持する。coalescedサンプルも保持する。既存の高密度回帰テストは100バッチ×1,000点＋開始点＝100,001点を保持し、同じ末尾座標の親イベントを二重追加しないことを確認している。
- 消しゴムも順序付き操作として保持する。古い線や消去履歴を単純に削ると、消去・書き直しの再現が変わるため整理していない。
- 以前の調査資料には、保存済み下書き最大99,272点、422応答4件、413未観測という記録がある。今回の実機警告を直接観測したわけではなく、点数上限は有力候補だが断定しない。本番データ・ログにはアクセスしていない。
- 容量判定は現行のまま。本文4MiB＋16KiB超は413、モデルのページJSON4MiB超・100,000点超・10,000操作超・200ページ超は理由付き422。形式異常やCSRF失敗の422を容量と扱わない。
- 一方のアカウントだけ警告が出ることは、復元した既存下書き、筆記サンプル数、消去・書き直し量、ページ数の違いで説明できる可能性があるが、今回の実機2アカウントの原因は未確定。通信障害や401・403・409・429・503も容量とは区別する。
- 従来は筆跡の終了ごとに2.5秒の保存待ち時間を延長し、連続筆記では保存開始が遅れる。保存要求は毎回全筆跡、成功応答も全筆跡で、保存済み内容の重複送受信が大きい。

## 実装

1. 2.5秒の待機は維持し、連続筆記でも最初の未保存変更から約10秒で完了済み筆跡の保存開始を試みる。進行中の保存は重ねない。ネットワーク待ち・長い処理・アクティブな筆跡の完了時刻まで10秒以内と保証するものではない。
2. `X-Draft-Response: acknowledgment` を送る新クライアントには、PUT成功でバージョンと更新時刻だけ返す。旧クライアントへは従来の全文を返す。GETは常に全筆跡を復元できる。
3. 新クライアントのGETで `append_supported: true` を交渉する。最後に確認した全筆跡と現在の履歴の先頭部分を、ページ番号・操作ID・順序・幅・ツール・色・全座標について比較し、完全一致するときだけ追加分を `append_data` として送る。既存履歴の変更・並び替え・削除・未知属性・旧サーバーでは全量保存へ戻す。
4. サーバーは既存の課題ロック内で生徒・教材・未提出状態・expected_versionを確認して追加分を結合し、既存モデルで累計の全データを検証する。新規下書きへの追加、曖昧な全量＋追加の同時指定、重複ID、不正座標、ページ変更、累計上限超過を拒否する。保存形式1、DB構造、上限、描画座標は変更しない。
5. 応答喪失後のGETが最後の送信スナップショットと一致すれば保存済みバージョンを採用し、同じデータを再送しない。新しい筆跡があればその分だけ次の保存を行う。別タブ更新は合併しない。
6. 初回復元・再試行のGETを重ねず、破棄済み画面へ遅延応答を復元しない。`append_data` を機密ログのフィルター対象に追加した。

これは座標の丸め・間引き・履歴削除ではなく、確認済み部分の送信省略である。保存される座標の全数と数値を維持する。100,000点／4MiBに達する警告そのものは解消していない。
容量超過時の筆記・消しゴム継続、未保存最新筆跡のPDF提出、離脱警告、正式提出前の保存待ち、署名付きコンテキスト、保存済みバージョン照合、提出UUID、25MiB上限、ストレージ失敗時の未提出扱い、採点ジョブ連携を維持した。

## 残るリスクと手動確認

- 累計100,000点・4MiBに達すれば引き続き自動保存は停止する。今回、数学品質を保って点数を大幅に減らす方式は確立していない。上限は推測で変更していない。
- 追加分方式でもサーバーは全データを検証・DBへ保存し、同課題のロックは従来のまま。DB・メモリ・多数ページ・上限近くの答案に対する本番性能を保証しない。
- iPad実機・Pencil実イベント・学校回線・30台のブラウザ同時PDF生成は未検証。描画コードを維持しても、定期保存時のスナップショット・比較の端末負荷は実機で確認が必要。
- 未保存部分はメモリにのみ残り、タブ終了・再読み込み・OSのタブ破棄で失われ得る。容量警告と離脱警告は維持する。
- 通信待ちが30秒を超えるとクライアントはタイムアウトする。サーバーが後から保存した場合は再確認し、不一致は強制上書きせず停止する。

実機での確認手順:
1. テスト教材でPencilによる短い数字・指数・分数・ルート・図形を連続20画以上書き、ペン・消しゴム各サイズ・指スクロール・ピンチ・素早い2画目を確認する。
2. 2.5秒以上休まず筆記を続け、完了済み筆跡が定期保存されることと、保存時に筆記が欠けないことを確認。保存済み後に開き直し、全筆跡・消去・書き直しを確認する。
3. テスト環境で下書きPUTだけ413／容量理由付き422に差し替え、追加筆記・消去後も容量警告が続くこと、そのまま提出したPDFに最新部分があることを生徒側・教師側で確認する。
4. 保存中に追加筆記して直ちに提出する。別テストで接続を切って復帰・再試行し、筆跡が残り、重複提出にならないことを確認する。
5. 同じ答案を2タブで開き、一方で更新後に古いタブから保存・提出する。409で停止し、手元の筆跡が残ることを確認する。教材変更の場合も同様に確認する。
6. 旧下書きを復元して続きから書き、追加分保存後も既存の数学記号が変化しないことを確認する。新旧クライアント混在時は別タブ競合を意図的に発生させ、上書きを拒否することを確認する。

元の作業ツリーと実験ファイル18件は開始時マニフェストでSHA-256一致を確認済み。測定イメージのアプリ3ファイルも最終作業ツリーとSHA-256一致を確認済み。フェーズAの報告後はユーザーの確認を待ち、フェーズBへ進まない。
