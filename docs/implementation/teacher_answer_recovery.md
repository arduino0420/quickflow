# 教師の答案再依頼（#159）

通常教師の答案詳細右パネルから、失敗した答案を再提出・削除せずに再依頼する。成功や正確なAI判定を保証するものではない。要確認の答案や完了済みの答案を再採点する機能ではない。

## 許可する範囲

- 読取結果が未保存: 失敗状態、既知のreading claim、現在の教材に一致する成功済み正答生成要求、妥当な保存済み正答、PDF実体・checksum、結果0件、queue安全性を確認し、読取から開始する。
- 読取済み: 既存の厳格な読取形式・状態検証と、#158の完全一対一照合を要求し、採点だけ開始する。正答は再生成しない。
- 停止候補grading: 経過時間では判断せず、保存読取・正答・PDF・世代とqueueを確認する。
- 不正読取、衝突・欠落・余分な読取、問題/教材不一致、由来不明、PDF欠損、既存結果・教師判定、完了済みは拒否する。通常採点の部分対応より厳格である。
- 所有教師・学校・配信先、CSRFと署名付き要求をPOSTでも確認する。生徒・guestは拒否する。

## 受付とqueueの境界

既存Submissionに `grading_recovery_attempts`、`grading_recovery_requested_at`、`grading_recovery_state` の3列を追加する。受付時には新しいSubmission/GradingResultを作成せず、復旧Jobが通常の採点処理で結果を作成する。元PDF・教材・有効な読取・教師判定を保護する。導入後のボタン受付は答案あたり最大3回、受付間隔60秒。過去のCLI操作回数は推定・補完しない。

GETは保存しない。対象・教師・元世代・入力指紋・状態を15分有効の署名に結び付ける。POSTはAssignment→Submission→関連入力の既存ロック順で再確認し、世代と受付回数を1つ進める。古い画面の再送は次世代を再開しない。primary DB更新が確定した後だけ標準ActiveJobでqueueへ登録する。呼出元の未確定トランザクションがあれば拒否する。

| 受付状態 | 意味と扱い |
| --- | --- |
| pending | primaryの受付確定。queue登録前に停止した可能性もある。再送しない |
| enqueued | queue登録の応答を得た。処理成功・採点完了とは異なる |
| uncertain | queue登録のfalse/nil/例外、または復旧読取後の採点登録不明。自動再登録しない |
| started | 対応世代・admissionを確認したJobがclaim取得。成功/失敗は既存Submission.statusで区別 |

pending/uncertainは画面を開き直しても無効ボタンと再送禁止の案内を表示する。遅れた正規Jobがclaimを取得した場合だけstartedへ進む。確認できない場合は運用担当が既存の読取専用診断で判断し、時間だけでqueueや受付を削除・再登録しない。元のCLI復旧・`recovery:inspect` は別の既存運用経路であり、今回のボタン受付の代わりに無断使用しない。

新世代を取得できない古いJobは、開始・保存・failed書込み・後続登録で拒否する。外部API待ちの間はDB行ロックを保持しない。queue応答とworker開始が逆順でも、startedをenqueued/uncertainへ戻さない。

## APIと表示

読取再開でも既存の5xx追加要求はupload＋reading全体で最大1回のまま。timeout・結果不明の自動再試行は増やさない。採点のみの復旧では読取APIを呼ばない。手動受付ごとに費用が発生し得るが、金額や外部側の処理回数・課金exactly-onceは保証できない。自動的な受付の繰返しはない。

failed時は右パネルを「採点に失敗しました」と薄赤の大きな「採点をもう一度依頼する」へ置換する。受付中はTurboがボタンを無効化するが、二重防止はサーバーでも行う。PDF実体が不明な時に保存成功を保証する文言は出さない。正常submitted/grading、完了結果、教師判定修正、PDF表示は維持する。

## 将来の配備・切戻し条件（本番では未実施）

- 本番migration、デプロイ、フラグ変更、実AI・既存答案の再処理は別途承認が必要。
- 新3列が必要。既存admissionの入力に受付回数・日時が加わるため、旧処理を安全に静止し、web・worker・登録元を同じ版へ整合させる。旧Jobを動かしたまま混在配備しない。
- 既存guestのmanifestはSubmissionの全属性を含むため、guest DBへの列追加はmanifest一致に影響する。現在のguestを自動migration・再seed・manifest再作成してはならない。将来guestも更新する場合は、別途承認されたschema/manifest移行の確認が必要。通常側だけの更新時はguestを現行コード・DBのまま維持できる。
- `QUICKFLOW_GRADING_RECOVERY_ENABLED` が厳密に `true` の時だけ受付可能。現在の本番値を推定せず、検証できた環境だけで解禁する。
- 問題時はまずフラグをOFFにし新規受付を止める。これは既に登録されたJobを取り消す操作ではない。実行中Job・queue・世代・receiptを確認し、コード切戻しを計画する。答案・結果・受付履歴を消すDB rollbackは行わない。
- 検証は架空データ/API doublesによるもので、実機や実API、本番答案の復旧成功とは区別する。
