# AWS Compose 移行計画（未実施）

この文書は将来の配備を判断するための計画です。ローカルComposeの追加、CI成功、PRの承認・マージだけでは本番配備を許可しません。**AWSでの起動・停止・配備・migrationは、この計画を最新の稼働状態に照合し、具体的な変更を所有者が承認してから行います。**

## 現在の境界を維持する

2026-11-09の読み取り確認では、通常版とゲスト版は別アプリ・別DB・別保存領域です。共有Caddyが入口となり、ゲストには専用Caddyもあります。DB/Caddy側にCompose管理情報がある一方、現在のアプリコンテナは後の配備手順で差し替えられています。AWS作業ディレクトリのComposeやGit HEADを、現稼働アプリそのものとみなしてはいけません。

- 通常版だけの移行でも、共有Caddyとゲストへの経路・TLS・認証・読み取り専用条件を維持する。
- ゲストの旧ベースや制限は意図的な運用であり、通常版へ無断で統合しない。
- 既存のvolume、bind mount、network、公開ポートを実測して対応表を作る。
- 既存DB/PDFを新しい空volumeに置き換えない。名前だけでなく、実際の接続先・mount元・所有者・用途を照合する。
- ローカルの `compose.yaml` / `compose.check.yaml` をAWSで直接実行しない。これらは架空AIを使うローカル専用設定である。

## 配備前にそろえる証拠

1. **コードとイメージ**: 承認したcommit、Gemfile.lockのhash、Ruby/OS依存、テスト済みimage ID/digestを記録する。`latest`というタグだけを根拠にしない。検証後に再buildした別イメージを無検証で配備しない。
2. **差分**: 現稼働通常版・ゲスト版と対象commitのコード、Gem、設定、schema、静的ファイルの差を説明する。古い本番コードで最新mainを上書きしない。
3. **実行設定**: 本番用Composeのservices、entrypoint、環境変数名、秘密値の供給元、network、volume、healthcheckをレビューする。秘密値をGit、CIログ、build context、イメージへ含めない。
4. **検証専用機構の排除**: 架空AI、ローカル用fixture、専用フラグ、検証用mountが配備構成へ入らないことを検査する。
5. **データ保全**: DBとPDFを整合する時点でバックアップし、隔離復元が成立することを確認する。バックアップの存在だけを復元可能性の証明としない。
6. **変更時間と影響**: 通常利用・採点中ジョブ・ゲストへの影響、停止時間の見込み、担当者、判定基準、切戻し期限を具体化する。

## 移行の順序（承認後のみ）

1. 変更直前にコンテナID、image digest、DB/PDF保存先、稼働ジョブ、既存設定を再確認する。調査時から変わっていたら計画を見直す。
2. 検証済みイメージを取得し、identityと実行設定を照合する。旧イメージと旧設定を保持する。
3. 新規受付と実行中ジョブの扱いを決める。処理中データを無視してworkerを強制終了しない。キューの排出・待機・再開方法とタイムアウト時の中止条件を定義する。
4. 必要なバックアップ・復元確認を完了する。
5. migrationが必要なら、起動とは分離した明示的な工程として実行する。通常の `bin/docker-entrypoint` はRails server起動時に `db:prepare` を実行するため、無意識に適用されない本番起動方式を用意・検証する。
6. 既存データを保つCompose管理への移行を、管理ラベル・名前・aliasの衝突を避ける手順で行う。新旧アプリが同じキューを意図せず同時処理しないようにする。
7. 入口の切替後、HTTPS、ログイン、権限、PDF取得、受付、worker、DB/PDF保存、教師修正・Excel、ゲスト隔離を確認する。`/up`だけで成功と判定しない。
8. 受入条件を満たした後に受付・ジョブ運用を通常状態へ戻し、結果と残る差を記録する。

## 切戻し

- **アプリだけの変更**: 旧image digestと旧実行設定へ戻す手順を事前に検証する。処理途中ジョブや新旧コードの同時実行による二重処理も確認する。
- **schema変更あり**: 旧版が新schemaを読めるかを事前に判定する。破壊的な変更後はイメージを戻すだけでは復旧できない。移行を段階化するか、承認済みの復元計画が必要。
- **データ復元**: 変更後に利用者が作ったデータを失う可能性があるため、自動で巻き戻さない。復元範囲、整合性、失われ得る更新を説明して判断を得る。
- **Compose設定のみの移行失敗**: 元の入口・コンテナ・network aliasを復元できることを確かめる。既存volumeを削除する `down -v` や全体pruneを切戻し手順にしない。

## 中止条件

対象DB/volumeの識別不一致、バックアップ・復元未確認、未説明のschema差分、ジョブの安全な停止が不明、ゲスト隔離の変化、未解決テスト失敗、秘密値・架空AI混入、承認範囲外の変更があれば、配備を始めない／次工程へ進まない。

ローカル検証は配備判断の材料です。実AIの精度・外部障害、実データ量、EBS性能、全端末の操作を自動的に保証するものではありません。
